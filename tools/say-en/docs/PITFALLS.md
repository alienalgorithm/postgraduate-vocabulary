# 踩过的坑

这里记的都是真事 —— 在做一个四千多段音频的 IELTS 阅读库时踩出来的。
每一条都写清楚：**什么症状、什么原因、怎么修、教训是什么**。

程序里那些看着多余的检查，几乎每一条背后都有一个这样的故事。

---

## 一 · 时间轴存成了秒，跟读一格不动

**严重程度：高**

### 症状

七篇文章的逐词跟读光标完全不动，停在第一个词上。
而且：

```
控制台 errors        0
音频文件             全在
音频能正常播放        是
所有守卫检查         全过
```

**一切看起来都正常。**

### 原因

`reader.js` 判断该高亮第几个词，是这么写的：

```javascript
var ms = audioEl.currentTime * 1000;      // currentTime 单位是秒
while (i + 1 < t.length && t[i+1] <= ms) i++;
```

而那七篇的时间轴存的是**秒**：`[0, 0.46, 0.67, ...]`。

于是 `ms` 是 460 的时候，`t[1]` 是 0.46 —— 循环第一次比较就
一路跳到最后一项，光标定死在句末。

### 怎么发现的

不是靠报错，是靠**量坐标**：

```python
pos = []
for _ in range(3):
    page.wait_for_timeout(700)
    pos.append(page.evaluate(
        '() => document.querySelector(".read-cursor").getBoundingClientRect().left'))
print(pos)      # [560, 560, 560]  ← 三次都一样，说明没动
```

修复后：`[164, 315, 361]`。

### 修法

```python
c['t'] = [round(x * 1000) for x in c['t']]
```

并加了一条硬检查：**时间轴末项必须 ≥ 1000**。
一句话读完至少一秒，末项小于 1000 就是存成秒了。

### 教训

> **「没报错」不等于「没问题」。**
> 有些故障是纯静默的 —— 数据结构合法、代码不抛异常、
> 功能就是不工作。这类只能靠量实际效果发现。

## 二 · voices 写成字符串数组，整套朗读放不出声

**严重程度：高**

### 症状

新做的一篇文章，点朗读按钮完全没反应。同样：

```
errors               0
音频文件             385 段全在
单独用 new Audio() 播放      能播
时间轴                毫秒、递增、不越界，全对
```

### 原因

`audio.json` 里写成了：

```json
"voices": ["bf_emma", "bm_george", "af_heart", "am_michael"]
```

而前端是这么读的：

```javascript
MV.voices.forEach(function(v) {
    opt.value = v.id;               // ← 字符串没有 .id
    opt.textContent = v.label;
});
```

`v.id` 是 `undefined`，音色下拉框全是空项，
播放函数拿不到音色，直接返回 —— 不报错，就是不出声。

正确的结构：

```json
"voices": [
  {"id": "bf_emma",   "label": "Emma · 英音女声"},
  {"id": "bm_george", "label": "George · 英音男声"}
]
```

### 教训

> **数据结构合法，不代表接口对得上。**
> JSON 解析通过、字段存在，不等于消费方能用。
> 这类问题只能靠端到端跑一遍发现。

程序里 `make_audio.py` 现在把 label 写死在常量里，就是防这个。

## 三 · 三十四段音频削波

**严重程度：中**

### 症状

听感上是重读处有轻微的毛刺失真，不仔细听发现不了。

### 原因

音频规格原本查八项，**全是元数据**：

```
音色数 · 音色全覆盖 · 时间轴对齐 · 时间轴递增
时间轴用毫秒 · 文件全落盘 · 生词音频齐 · 语速合理
```

**一次都没解码过音频本身。**

解码之后一查，全库 34 段峰值触顶 1.000，集中在 `am_michael`
这个音色 —— 它输出音量偏高，重读处顶到了上限。

### 修法

```python
peak = float(abs(wav).max())
if peak > 0.95:
    wav = wav / peak * 0.95
```

存量的 34 段解码后归一，重新编码（不重新合成，所以时间轴不受影响）。

### 教训

> **元数据全对，不代表声音是对的。**
> 要听得过去，就得真去解码看波形 —— 削波、过轻、
> 轴超出时长，这三样都是元数据看不出来的。

这就是 `say.py` 里 `inspect()` 存在的理由。

## 四 · 时间轴末项超出音频时长

**严重程度：中**

### 症状

一句话的最后几个词永远高亮不到，光标提前停住。

### 原因

时间轴末项是**最后一个词的起点**，正常应该小于音频总时长
（后面还有那个词本身加尾音）。

但重新编码之后音频时长会略微变化，
有 31 段的末项超出了实际时长几十到几百毫秒。

### 修法

```python
if c['t'][-1] / 1000 > dur:
    lim = int((dur - 0.03) * 1000)          # 留 30ms 余量
    t = [min(x, lim) for x in c['t']]
    for i in range(1, len(t)):              # 截完还要保证递增
        if t[i] < t[i-1]:
            t[i] = t[i-1]
    c['t'] = t
```

**截完必须重新检查递增** —— 多个值被截到同一个上限的话，
就不再严格递增了。

### 教训

> **改了一处，回头找所有依赖它的地方。**
> 重新编码改变了时长，而时间轴依赖时长 —— 这种隐形依赖最容易漏。

## 五 · 一次跑完被系统杀掉

**严重程度：中**

### 症状

批量合成 286 段，跑到第 25 段时进程消失。

```
控制台输出          没有任何报错
退出码              没打印出来
dmesg               看不到 OOM 记录（容器里往往看不到）
```

### 原因

内存 3.9 GB，模型加载后本身占一大块，
再加上累积的波形数据，被系统 OOM killer 直接杀掉。

**它不会给你机会打印任何东西。**

### 修法

三件事：

```python
# 1  断点续跑：先读已完成的
if os.path.isfile(out):
    old = json.load(open(out, encoding='utf-8'))
    MV, AUDIO = old['MV'], old.get('AUDIO_DATA', {})

# 2  跳过已做的
if key in MV['audio'][v]:
    continue

# 3  增量存盘：每 8 段存一次
if done % 8 == 0:
    json.dump({'MV': MV, 'AUDIO_DATA': AUDIO}, open(out, 'w'), ...)
```

加上 `--n` 限流，反复跑同一条命令就能推进。

### 教训

> **长任务必须能断点续跑。**
> 不是为了优雅，是因为它一定会在某个时候被打断 ——
> 超时、内存、断网。第一次做的时候我没加，白跑了 25 段。

## 六 · 自动修繁体字，把「毫无」改成了「殚无」

**严重程度：中**

### 症状

写了个自动修复器，用 opencc 把繁体字转简体。
跑完之后发现译文里的「毫无吸引力」变成了「殚无吸引力」。

### 原因

opencc 的 `t2s` 是**逐字转换，不看词义**。
「毫」在繁简两套字集里都存在，但它还是被转了。

### 修法

加**往返校验** —— `t2s` 再 `s2t` 能回到原字才转：

```python
cc = opencc.OpenCC('t2s')
back = opencc.OpenCC('s2t')

sim = cc.convert(ch)
if len(sim) == 1 and sim != ch and back.convert(sim) == ch:
    # 只有往返稳定的才是真繁体
    replace(ch, sim)
```

效果：

```
毫 → 毫 → 毫    不转 ✓
著 → 著 → 著    不转 ✓
么 → 么 → 麼    不转 ✓
絲 → 丝 → 絲    转  ✓
糹 → 纟 → 糹    转  ✓
後 → 后 → 後    转  ✓
```

### 教训

> **自动修复必须带安全闸。修错了比不修更糟。**
> 检测可以宽松（多报几个人来看），修复必须保守。

这一条与音频无关，但它是**所有自动修复的通用原则**，
所以 `say.py` 里的峰值归一只做缩放，从不改动波形形状。

## 七 · 「元数据全对」的假象反复出现

**严重程度：认知层面**

前面第一、二、三条其实是同一个问题的三次发作：

| 次数 | 元数据 | 实际情况 |
|---|---|---|
| 一 | 时间轴项数对、递增、文件全在 | 单位错了，跟读不动 |
| 二 | JSON 合法、字段存在、音频能播 | 结构错了，放不出声 |
| 三 | 八项检查全过 | 从没解码过，34 段削波 |

三次都是：**该查的没查，查了的全过。**

所以 `say.py` 的 `inspect()` 是解码之后看波形的，
而不是读文件头的元数据。

> **能量身检查的，就别只看体检表。**

## 八 · 浮点尾差被误当成 bug

**严重程度：低（但会浪费时间）**

### 症状

同一句话重新合成一遍，与之前的文件不一样：

```
              新合成      旧的
时长          10.560     10.325
峰值           0.761      0.695
RMS           0.0897     0.0885
```

一度怀疑模型下错了版本。

### 原因

**这是正常的。** ONNX 推理的浮点运算顺序在不同 CPU、
不同线程调度下有细微差别，神经网络层层放大就有了尾差。

模型本身核对过 MD5，完全一致：

```
kokoro-v1.0.onnx   9579b435abd94a5af3d00d3cd39df548
voices-v1.0.bin    29895103243c07818862043c051e1db0
```

### 判断标准

不要比对波形是否逐位相同，比对**质量指标**：

```
时间轴项数 = 词数        ✓
毫秒制、严格递增          ✓
峰值 < 0.95              ✓
```

这三条一致，就是等价的。

### 教训

> **量之前先确认尺子准不准。**
> 曾经按一份有问题的检测数据去「修」译文，
> 结果九处报警全是虚警 —— 差点把对的改成错的。
