# 出片（虫洞路线）：本机只做 1080p 检查片段，推送后由 GitHub 出 4K

变量：{作品目录} {工作目录} {片名} {英文短名} {分支} {配乐} {发布} {段数} {说明} {检查片段} {封面} {本机配乐}

本机配乐 {本机配乐} 不存在时，先跑 `bash 动画工坊/tools/music/decrypt_music.sh {作品目录}`（有 MUSIC_KEY 解主配乐，没有就用备用），改用解出的 `{作品目录}/music/score.wav`（.gitignore 挡住不会提交；以后跑 package_music.sh 前要先删掉它）。

先读 `{作品目录}/BRIEF.md`，遵守全部规则。4K 整片只在 GitHub Actions 上出（`.github/workflows/anim-render.yml`，按帧号分 {段数} 段并行渲染，失败自动重试，再拼接、混音、核对、出 1080p）。本机 CPU 和磁盘都紧张，只做下面的小检查，临时文件放 `{工作目录}/tmp/`，用完删大文件。

1. 本机检查（只查片子本身，几分钟）：
   - `python3 动画工坊/tools/ci/check_story.py {作品目录}`；`python3 动画工坊/tools/ci/text_rules.py {作品目录}`；
   - `python3 动画工坊/tools/ci/stills_qa.py {作品目录} --out {工作目录}/tmp/qa`（还没有 qa/ref 参考图就加 `--no-ref`）；
   - 1080p 检查片段，只出这些时间段：{检查片段}。每段 `node {作品目录}/engine/render.js --from <a> --to <b> --scale 1 --parallel 2 --audio {本机配乐} --out {工作目录}/tmp/check_<a>.mp4`，用 `python3 动画工坊/tools/ci/verify_video.py` 核对帧数和音轨，抽几帧 Read，看完删掉。
   有质量问题（字、画面、声音）就先修好再往下走；不是质量问题的不许卡住流程。
2. {封面} 为 yes 时：用 `node {作品目录}/engine/still.js --scale 2` 在最强的名场面出图，做两张 B站 封面 `{作品目录}/out/cover_16x9.png`（3840×2160）和 `cover_4x3.png`（2880×2160），配短而大的标题；写 `{作品目录}/out/bilibili.md`：3 个诚实又吸引人的标题（不用 最、第一、保证）、简介、出处列表（来自 EVIDENCE.md）、配乐署名（和 music/LICENSES.md 完全一致）、标签。
3. 提交和推送：
   - 写 `动画工坊/渲染请求.json`：`{"id":"{英文短名}-<date -u +%Y%m%d%H%M%S>","film":"{片名}","scale":2,"fps":60,"from":null,"to":null,"music":"{配乐}","shards":{段数},"release":{发布},"note":"{说明}"}`；
   - 确认没有明文音频要进仓库：`git status --porcelain` 里不许出现 music/backup/、music/cc0/ 以外的 .wav .mp3 .flac .m4a .ogg；
   - `git add --sparse {作品目录} 动画工坊/渲染请求.json`，中文提交说明，`git pull --rebase origin {分支}`，`git push origin HEAD:{分支}`；网络失败按 2、4、8、16 秒重试最多 4 次。先看 anim-render.yml 的 on.push.branches，确认 {分支} 在里面。
4. 跟踪 GitHub 上的运行（只用 api.github.com 的读接口，代理已鉴权；不用 gh 命令；不碰 secrets 之类接口）：
   - 仓库 owner/repo 从 `git remote get-url origin` 的最后两段取；
   - `GET /repos/<owner>/<repo>/actions/runs?head_sha=<推送的提交>` 找 path 为 `.github/workflows/anim-render.yml` 的运行，同一次推送触发的 anim-check 也一起看；
   - 用一个后台 until 循环每 60 秒查一次状态，最多等 240 分钟，不要高频轮询；
   - 结束后 `GET /repos/<owner>/<repo>/actions/runs/<id>/jobs`，再对每个作业 `GET /repos/<owner>/<repo>/check-runs/<作业id>/annotations` 读 ::notice:: 注解：每段 fps、总帧数、积分响度、真峰值、用了哪种配乐。
5. 判断：
   - 成功的标准只看片子：总帧数等于 round(片长×60)，音轨和画面等长，真峰值按 verify_video.py 的标准（AAC 编码后不超过 0 dBTP），积分响度在 -14 LUFS 左右，anim-check 通过；
   - 配乐写着 backup 而请求的是 main：多半是 GitHub 上还没加 MUSIC_KEY 仓库密钥。这不是失败，写进 notes，提醒仓库主人在 Settings > Secrets and variables > Actions 加 MUSIC_KEY；
   - 运行失败：先读注解判断原因。质量问题就修好后从第 1 步重来（最多 2 轮）；不是质量问题（运行器、网络、下载）就换一个新的 id 再推送一次请求（最多 2 次），不要卡住。
6. {发布} 为 true 时：`GET /repos/<owner>/<repo>/releases/tags/<tag_prefix>-r<run_number>`（tag_prefix 在 `{作品目录}/film.json`）拿到 Release 链接。

返回 ok、notes、run_url、release_url、metrics（frames、fps、lufs、true_peak、music）、files。
