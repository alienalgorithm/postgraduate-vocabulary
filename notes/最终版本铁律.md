# 最终版本铁律

## 第零条 · 不存在任何外部词汇表

**文章质量优先于选词，永远。**

选题自由，先把文章写到最好，再从写好的文章里挑出 50 个加粗词。
**绝不从任何词汇表取词，绝不为了塞词而改动英文。**

白送词（Zipf ≥5.0）的正确处置是**取消它的加粗、把名额让给同段另一个词**，
自然的说法留在正文，只是不占名额。

唯一的词汇硬约束是**跨篇不重复（含同根）**——它不扭曲英文，
因为撞车时可以改加粗别的词，不必改句子。

> 2026-08-16 彻底清除：数据层的 `vocabTotal: 2545` 与
> `vocabNote: "新东方考研英语词汇 · 乱序版"`（10 个文件）、
> 网站首页的「尚待使用 N 个词元」统计、词库页的「N 个待用」统计。
> 那个池子从来不存在于代码里，只存在于旧描述与我的汇报中，
> 却足以在选题时把文章往「凑词」的方向拉。


## 第零条之二 · 指标不许反过来指挥文章

**任何指标，只要它会制造「为达标而动文章」的压力，就必须撤掉或降级。**

已经发生过三次：

| 指标 | 它逼我做了什么 |
|---|---|
| 词数上限 270 | 削到 270 就停手，13/23 篇卡在整十 |
| 词价 Zipf≥5.0 | 把 blood groups 改成 blood antigens、kitchen hand 改成 scullery worker |
| **分布跨度 ≥5**（我自己加的） | 会逼我为让跨度变大而把某篇撑长或削狠——**已撤掉** |
| **词数不许整十**（我自己加的） | 逼我为脱离整十而逐篇削一个词，如 The inquest of 1628 → The 1628 inquest——**已撤掉** |

**词数只剩一条规则：249—271。** 落在哪里由减法轮决定，不看整齐不整齐。
为「凑到 270」停手和为「凑到不是 270」削词，是同一个毛病的两面。

**判据**：一条指标若答不上「达不到时该改哪里，且那处改动本身就是改进」，
它就不是质量指标，是凑数指标。

**声明在先的体式不是指纹，不声明的巧合才是。**
十四行诗永远十四行没人说是机器写的；而「13 篇恰好 270 词」是贴上限停手的痕迹，
因为 270 不是有意义的数，只是当时允许的最大值。
体式已明写入 README「体式」一节。


## 第零条之三 · 质量是目的，词数与重点词都只是形式

**在 249—271 之间，把文章写到质量最高——这是唯一的要求。**

词数、50 个重点词、10·10·10·10·10 的分布，全是形式。
**形式挡了质量的路，就让形式让路。**

### 一 · 不许为凑字数而写句子

一句话若不是论证需要的，它就不该在里面——**不管当前词数是多少**。
反过来，论证需要的句子也不许为了压词数而删。

已犯过两次，方向相反、性质相同：
- 削到 270 就停手（凑到上限）
- 为脱离整十而逐篇删一个不冗余的词（凑到不是上限）

**判据：这一处增删，若不能只凭「文章因此更好」四个字说清楚，就是凑数。**

### 二 · 不许为凑满 50 个而硬塞重点词

**重点词是从写好的文章里挑出来的，不是往文章里塞进去的。**

若某个名额只能靠扭曲句子才能塞下，**宁可让这一段少一个、由别段补上**；
若全篇都补不上，**说明这个题材本来就撑不起 50 个词——该换题材，不该扭文章**。

### 三 · 每一个重点词的用法必须绝对正确

它出现在那里，必须是**母语者在那个语境下真会用的那个词**。

三条硬判据：
1. **不是为避开某个指标而换上来的。**
   曾为避开 Zipf≥5.0 把 `blood groups` 改成 `blood antigens`
   （1980年代法庭说的就是 blood groups）、`kitchen hand` 改成 `scullery worker`
   （scullery 是维多利亚时代的词）、`for nothing` 改成 `idly`
   （idly 是「懒散地」）——五处全部退回，其中两处还伤了史实准确度。
2. **不是技术上能用、实际没人这么说的词。**
   曾为避开词冲突把 `deck` 改成 `planking`——人在甲板上跑，不在「铺板」上跑。
   **冲突只约束加粗名额，不约束正文用词**：`deck` 不能加粗，但可以不加粗地用。
3. **词性、搭配、时代都对。**
   `overbuilt` 形容「建得过多」，不能形容一艘船的状态；
   `unbroken` 是「没断」，对整船打捞不自然，本词是 `salvage`。

**读者看完应当觉得「这些词用得真准」，而不是「这些词是硬凑上去的」。**

### 四 · 白送词与冲突的正确处置

不是改英文，而是**取消它的加粗、把名额让给同段另一个词**。
自然的说法留在正文，只是不占名额。


## 铁律与检察官的对照

```bash
python3 scripts/inspector.py --charter
```

`data/reference/charter-map.json` 把每条规则挂到它执行的铁律条款下。两个用途：

**一 · 检察官报告时直接引用铁律。** 例如：

```
·待核 [FIT-02] §1 单句加粗密度 4/7 = 57%　　铁律第零条之三·二
·待核 [SRC-02] 4 条含数字或专名的史实无来源　　铁律史实
```

看得见「这不是随口定的，是铁律哪一条」。

**二 · 反查覆盖：哪些条款没有任何规则在执行。**
那些条款只能靠人的自觉，是这套机制真正的薄弱处。

当前 12 条款中，**只有第零条之二无规则执行**——而这是必然的：
它管的正是「该不该有这条规则」，规则管不了自己。
已据它撤掉三条：词数上限当目标、词数不许整十、分布跨度≥5。

两条测试锁住这套映射：
- 映射里的规则都真实存在（防「铁律以为有人在管，其实没有」）
- 每条规则都挂在某条铁律下（防「规则在跑，却说不出执行的是什么」）

## 一、什么才算“最终版本”

当用户或当前任务明确把一版称为“最终稿、最终精校稿、最终精进稿、锁定稿”，或明确判断某一精进版优于现有稿并要求继续按最终标准推进时，该版本即成为待同步的最新最终版本。

最终版本同时包括英文正文、中文译文、50个重点词、速查表、史实核对、来源、标题、导语、状态、日期和指标。任一部分不同，都属于不同版本。

## 二、原子同步铁律

新的最终版本形成后，必须在同一次任务中同步：

1. 权威数据文件：`data/articles.js` 或 `data/article-NN.js`
2. 生成稿：`articles/NN-*.md`
3. 网站：首页、文章阅读器和词库入口
4. `README.md`
5. `notes/对话交接文档.md`
6. 对应入库记录
7. `data/final-version-manifest.json`
8. 永久校验规则

不得出现“聊天里已经改好，但GitHub仍是旧稿”的状态。

## 三、旧稿淘汰铁律

- 新最终稿进入 `main` 后，前一版立即失去权威性。
- 旧稿只允许存在于Git提交历史中，用于追溯；不得继续存在于活动数据文件、正式Markdown、网站内容或长期开发分支中。
- 不得保留 `final-v2`、`final-new`、`latest-final` 等并行活动文件。每篇文章只能有一个活动权威版本。
- 版本回滚必须由用户明确要求；任何自动化、生成脚本或后续模型都不得自行恢复旧稿。

## 四、云端完成判定

只有同时满足以下四项，才能声称“已经存到云端”：

1. 新版本已提交并合并到 `main`；
2. 从 `main` 重新读取，正文与指标确为新版本；
3. GitHub Actions全量校验为 `success`；
4. README、交接文档和最终版本清单均已同步。

分支、PR、聊天文本或本地文件都不能单独算作云端最终完成。

## 五、内容指纹铁律

- `data/final-version-manifest.json` 为每篇文章保存完整内容指纹。
- 指纹覆盖标题、导语、状态、指标、英文、中文、速查表、史实与来源。
- `node scripts/final-version-guard.js` 必须在每次PR和主分支提交中运行。
- 标题相同、词数相同但正文不同，指纹仍会变化，校验必须阻止未登记的覆盖。

## 六、后续固定流程

1. 写作或精进完成；
2. 明确最新最终稿；
3. 立即更新全部权威表面；
4. 重新生成Markdown；
5. 更新最终版本清单与指纹；
6. 运行全库校验；
7. 合并到 `main`；
8. 回读 `main` 并确认CI成功；
9. 删除承载旧稿或已合并稿的临时分支。

未完成第8步，不得结束任务。
