# 使用手册

> 按「你要做什么」组织，不按工具名组织。
> **只有三条命令必须记住**，其余都是可选的深度。

---

## 必须记住的三条

```bash
python3 scripts/agent.py brief notes.txt     # 动笔前：拿可用词池
python3 scripts/inspector.py 23              # 随时：查这一篇
python3 scripts/preflight.py                 # 推送前：一条命令查全部
```

其中 **`preflight` 是唯一忘不掉的那条**——它把其余所有检查都跑一遍，
包括本地跑不到的 CI 那一步。忘了别的都没关系，忘了它就会出事。

---

## ★ 跑多少轮？实测答案：不看轮数，看是哪一类

18 篇跑下来，抓到问题的来源分布：

| 来源 | 抓到 | |
|---|---|---|
| **史实核查（上网逐条核）** | **11 处** | 最多 |
| **刁钻一问＋最弱一句（人读）** | **7 处** | 次之 |
| 机器十五层规则 | 6 处 | |
| 句序／接缝／因果／中文／词价／母语者 | **约 2 处** | 最少 |

**最致命的三处全部来自人读，机器永远抓不到：**

- 第04篇 `granted **him** £8,750` —— him 紧跟 Kendall，而**获奖的是 Harrison**
- 第07篇 `named it entropy` —— **「熵」这个名字是冯·诺依曼建议的**
- 第13篇 `the first woman` —— **居里夫人 1911 年就独得过化学奖**

### 所以对已定稿的文章，跑这三件事就够

```bash
python3 scripts/regress.py NN snapshot     # 1 存快照
python3 scripts/inspector.py NN            # 2 十五层，逐条判
python3 scripts/polish.py NN round 9       # 3 刁钻一问＋最弱一句
#   并对每条 facts 上网核实，核过的写明「已核」并附链接
```

**检察官第十五层 AUD 会主动催这三件事**——没做完就报 AUD-01/02/03。

### 中间那八九轮呢

它们**在「写」的时候有用**——第21、22、23 篇写作时靠它们改了十几处。
**但对已定稿的文章边际收益极低**，18 篇里合计只抓到约 2 处。

**写新篇：跑满十三轮。核旧篇：跑那三件事。**

## 场景一 · 写新的一篇

```bash
# 1 研究笔记写成 notes.txt，取词池
python3 scripts/agent.py brief notes.txt
#   给出四组：可用高价值词 / 题材必需生僻词 / 必须避开（含同根）/ 白送词
#   ★ 从「可用」里挑满 50 个。绝不能写完再查重——撞车要重写整句

# 2 写英文五段 → 写中文五段（先写自然的，再落加粗与括注）

# 3 草稿体检，反复跑到阻塞项为 0
python3 scripts/agent.py review draft.md

# 4 入库到 data/article-NN.js
#   ★ 速查表必须按「英文加粗顺序」建，不能按中文括注顺序

# 5 检查
python3 scripts/build_markdown.py            # 全库结构 + 跨篇冲突
python3 scripts/inspector.py 23              # 十层规则

# 6 十一轮精修（守门器不许跳轮、不许敷衍）
python3 scripts/polish.py 23 status
python3 scripts/polish.py 23 next
python3 scripts/polish.py 23 log 3 --pos … --before … --after … --why …
python3 scripts/polish.py 23 done 3 --note "改了…／没改…／因为…"

# 7 存快照，让以后的改动受 REG 层保护
python3 scripts/regress.py 23 snapshot

# 8 推送前 + 出单篇文件
python3 scripts/preflight.py
python3 scripts/export_one.py 23
```

配套提示词：`notes/第22篇写作提示词.md`（改篇号即可复用）

## 场景二 · 改一篇已有文章 ★ 新功能在这里

**这是最容易把东西改坏的场景**，本项目已发生六起——每一起当时都通过了全部合规检查。

```bash
# 1 ★ 动手之前先存快照。不存 = REG 层不工作
python3 scripts/regress.py 22 snapshot

# 2 改。改之前先把真实文本读出来再替换，用 assert 校验匹配
#   （凭记忆构造匹配串曾一次改坏三篇）

# 3 检查 —— 检察官自动带上 REG 层，直接告诉你「改坏了什么」
python3 scripts/inspector.py 22

# 4 确认无碍，把当前状态设为新基准
python3 scripts/regress.py 22 accept

# 5 推送前
python3 scripts/preflight.py
```

**全库快照已经存好（22/22）**，所以第 1 步只在你写了新文章后才需要。
`preflight` 会检查覆盖率，缺哪篇会直接告诉你。

### REG 层会替你盯住九件事

| 编号 | 它盯的 | 曾经的事故 |
|---|---|---|
| REG-01 | 标题的词还在正文里吗 | 为省词删掉 question，而标题是 Only That **Question** Had a Number |
| REG-02 | 导语的数字还在正文里吗 | — |
| REG-03 | 新增悬空代词了吗 | `at the Vasa Museum` 压成 `there`，先行词全篇消失 |
| REG-04 | 段落接缝变松了吗 | — |
| REG-05 | 白送词／边缘词变多了吗 | — |
| REG-06 | 句长节奏变平、短句连排了吗 | 三个 7—9 词短句连排 |
| REG-07 | 无施事被动变多了吗 | — |
| REG-08 | 邻句实词重复变多了吗 | — |
| **REG-09** | **引入了语料里从没出现过的搭配吗** | `ran across her upper planking`——人在甲板上跑，不在「铺板」上跑 |

**REG-09 是最有用的一条**：它拿 446 万词语料，只判断**这次改动新引入的搭配**。
原文里语料没收录但读着没问题的，一概不管。

### 第13轮极限轮：唯一一条「不能当场跑完」的轮次

它审的是**判过「保留」的地方**——与第八轮不同，第八轮读台账、读的是**改过**的地方。
一篇否决了五条提案的文章，第八轮一条都不会碰那五条。

**但它必须隔一次会话再跑。**

> 2026-08-16 曾一度撤销此轮，理由是「实跑两次零翻案」。**那个理由是错的**：
> 那两次都是在做出判断的同一次会话里跑的——理由还在脑子里，
> 遮住的只是纸面，不是记忆。**零翻案不能证明它没用，只能证明测错了。**

所以正确的用法是：一篇跑到第12轮就收工，**下次开新对话时再跑第13轮**。
`polish.py NN status` 会一直提示它没跑完。

## 场景三 · 判断一篇到底改完没有

```bash
python3 scripts/polish.py 22 status          # 十一轮进行到哪
```

十一轮跑完 ≠ 到临界点。**还要跑对抗式审计**，配套提示词
`notes/临界点审计提示词.md`：强制产出**至少五条**改进提案，逐条算代价，
**五条全被代价否决才算到**。

> 第22篇的实际路径：十一轮 → 宣布到了 → 审计 → 又找出三条 →
> 改完 → 再审计 → 全否决 → 才是真的到了。
> **一遍就宣布「到了」是不可信的。**

## 三条纪律

**一 · 改之前先把真实文本读出来。**
用 node 从数据层取出该段原文再替换，并用 `assert` 校验。
凭记忆构造匹配串曾一次同时改坏三篇。

**二 · 每次改完回跑 `inspector.py <篇号>`。**
约三分之一的新缺陷是修改时引入的。

**三 · 指标一改要同步三处。**

1. `data/*.js` 的 metrics
2. `scripts/final-version-guard.js` 里 README / 交接文档的行校验
3. `.github/workflows/validate-content.yml` 的硬编码期望值 ← **本地跑不到**

`preflight` 会查第三处。两次「本地全绿、CI 却红」都栽在这里。
